# meerkly-sdk

The Meerkly exit-node SDK. Embed it in an app or service and that host shares
its connection with the [Meerkly](https://meerkly.com) network: it holds one
QUIC connection to a gateway, and proxy traffic leaves through its IP. Earners
are paid per GB, metered on the gateway.

An exit node identifies itself only by a **publisher id** (`pub_…`) from
[dashboard.meerkly.com](https://dashboard.meerkly.com). It is a public
identifier, not a secret.

## How it works: everything builds from the Rust SDK

There is one exit-node implementation, written in Rust, in
[`crates/client-core`](crates/client-core). It does all the actual work:
- the QUIC connection
- registering with the gateway
- reconnecting and failing over
- proxying each request
- refusing private targets

Every other package is a thin wrapper that exposes that same compiled core to
another language. None of them reimplements any of it.

```
crates/protocol          wire types shared with the gateway
      │
crates/client-core       THE SDK. All behaviour lives here.  → crates.io  meerkly-sdk
      │
      ├── crates/client-napi   napi-rs binding  → sdk/node     → npm  @meerkly/sdk
      │
      └── crates/client-ffi    uniffi binding (one cdylib, libmeerkly)
              ├── sdk/android  Kotlin + per-ABI .so in an AAR  → Maven Central  com.meerkly:sdk
              │       └── sdk/expo   Expo module over the AAR   → npm  @meerkly/expo
              ├── sdk/swift
              ├── sdk/python
              ├── sdk/go       (uniffi-bindgen-go)
              └── sdk/ruby
```

### Source of truth

| What | Source of truth | Everything else |
|---|---|---|
| Behaviour | `crates/client-core` | Bindings only forward calls; a fix here reaches every language on the next build. |
| Wire format | `crates/protocol` | The gateway (closed source) builds against this same crate. |
| Public API shape | [`crates/client-napi/src/lib.rs`](crates/client-napi/src/lib.rs) for Node, [`crates/client-ffi/src/lib.rs`](crates/client-ffi/src/lib.rs) for every uniffi language | The language files under `sdk/` are **generated** from these. |
| Version | `[workspace.package] version` in [`Cargo.toml`](Cargo.toml) | Stamped into npm and Maven at release time. `sdk/expo/package.json` is the one hand-kept copy, and CI fails if it drifts. |

### Generated files: never edit by hand

These are generated but committed, so each language can be read and consumed
without a Rust toolchain. Change the Rust binding crate instead, then
regenerate:

| Files | Generated by | Regenerate with |
|---|---|---|
| `sdk/node/index.js`, `index.d.ts` | napi-rs | `./scripts/build-node-addon.sh` |
| `sdk/android/lib/src/main/kotlin/com/meerkly/sdk/meerkly.kt` | uniffi (config in [`crates/client-ffi/uniffi.toml`](crates/client-ffi/uniffi.toml)) | `./scripts/build-android-sdk.sh` |
| `sdk/swift/*`, `sdk/python/meerkly.py`, `sdk/ruby/meerkly.rb` | uniffi | `./scripts/build-ffi-bindings.sh` |
| `sdk/go/meerkly/*` | uniffi-bindgen-go | `./scripts/build-ffi-bindings.sh` |

Native libraries (`.node`, `.so`, `.dylib`, `.dll`) are never committed. They
are built per target by the scripts, by CI and by the release workflow.

Hand-written code is limited to these places:
- the two binding crates
- `sdk/expo` (a TypeScript API and config plugin over `com.meerkly:sdk`; Android only)
- `sdk/go/cmd`
- the Gradle and npm packaging

### Making a change

- **Behaviour** (a bug, reconnect logic, a new guard): edit `client-core`.
  Nothing else changes, and every SDK picks it up at the next release.
- **API** (a new option or method): add it in `client-core`, then expose it in
  **both** `client-napi` and `client-ffi`, then regenerate the bindings and
  commit the output. If `sdk/expo` should expose it too, forward it in
  `sdk/expo/src` and its Kotlin module.
- **Protocol** (a new frame or field): edit `crates/protocol`. The gateway has to
  understand the change before any exit sends it. Land it here, update the gateway
  to it, and deploy the gateway before releasing SDKs that
  depend on it.

CI builds every one of these on every push: all five Node targets, the Swift
typecheck, the Android AAR loaded on an emulator, and both Expo example-app
builds. The end-to-end smokes, where an exit node proxies a real request, need
the gateway, so they run in the private gateway repo.

## Releasing

Every SDK releases at one synced version: `[workspace.package] version` in
`Cargo.toml`. `sdk/expo/package.json` must match it.

1. Bump both, commit, and push to `main`.
2. Push the tag `v<X.Y.Z>`. `release-sdks` builds every SDK on every platform,
   and publishes to npm, crates.io and Maven Central only if all of them
   succeed. There is no manual step.

Only repo admins can push `v*` tags, and the publishing secrets are only
released to runs started by one.

See the comments at the top of
[`.github/workflows/release-sdks.yml`](.github/workflows/release-sdks.yml) for
why every build must pass before anything is uploaded.
